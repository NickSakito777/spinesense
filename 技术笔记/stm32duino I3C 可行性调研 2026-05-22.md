# stm32duino I3C feasibility investigation (2026-05-22)

> Historical research note, translated in September 2026. Claims, confidence labels, estimates and unresolved items below retain their status as recorded on 2026-05-22; they have not been silently updated. For the current tested collection workflow, see the [Tom handoff](../docs/tom-handoff/README.md).

> Three independent agents investigated in parallel: (1) the stm32duino framework's I3C ecosystem, (2) the engineering effort to adapt the ISM6HG256X library for I3C, and (3) HAL_I3C API + SETDASA + internal pull-up code templates. This note combines the three reports and grades their confidence.

## One-sentence conclusion

**Feasible, and much faster than expected.** Running multiple ISM6HG256X devices over I3C on the STM32U385 within stm32duino was estimated at 28–44 h (≈ 1 week); **on 5-22, N=5 reached ALL_PASS in one day of testing**. The key shortcut: the stm32duino BSP exposes the `HAL_I3C` API directly. A sketch can use `extern "C" { #include "stm32u3xx_hal_i3c.h" }`, so **there is no need to modify the transport layer of the stm32duino/ISM6HG256X library**. This shortcut was not considered in the Path A estimate; see Path C below.

The stm32duino main repository was checked and does contain a native I3CBus library, but the locally installed `STMicroelectronics:stm32@2.12.0` release does not yet include `libraries/I3C`. Today's Arduino approach primarily calls STM32 HAL_I3C directly from the sketch and was stable in testing (see [Multi-IMU I3C Bring-up Procedure (2026-05-22; N=3–5 Hardware Testing)](I3C%20%E5%A4%9A%E9%A2%97%20IMU%20bring-up%20%E5%AE%9E%E6%93%8D%202026-05-22.md) §5b, actual code). Manually importing the main-branch library remains an option to reduce future implementation effort, but is no longer urgent.

**Internal pull-up test:** N=5 with ~30 cm jumper wires achieved connectivity ALL_PASS, **without external pull-ups**. The 5-18 note's “marginal 170–246 ns” estimate was conservative.

## Key findings, ordered by confidence

### [High confidence] Actual STM32U385 internal pull-up API name

Correct case: `HAL_PWREx_EnableI3CPullUp(PWR_I3CPU_PB13)` — capital U; the macro names a specific pin.

- Function: `HAL_PWREx_EnableI3CPullUp` (`EnableI3CPullup`, with a lowercase u in the 5-18 note, was a typo).
- Macro: `PWR_I3CPU_PB13` / `PWR_I3CPU_PB14` / other candidate pins (`PWR_I3CPUx_PIN` in the 5-18 note was a placeholder, not an actual macro).

Source: `stm32u3xx_hal_pwr_ex.h` in `stm32duino/Arduino_Core_STM32`.

### [High confidence] STM32CubeU3 has a NUCLEO-U385RG-Q I3C SETDASA example

URL: https://github.com/STMicroelectronics/STM32CubeU3/tree/main/Projects/NUCLEO-U385RG-Q/Examples/I3C/I3C_Sensor_Private_Command_IT

- Interfaces with LSM6DSV16X (same-generation I3C IP as ISM6HG256X, with a shared PID register-layer structure).
- `main.c`: 668 lines, complete single-device SETDASA flow.
- Key API locations:
  - L69–71: `TargetDesc_TypeDef *aTargetDesc[N]` array (extension point for N devices).
  - L76: `aSETDASA_LSM6DSV16X_data[1] = {(TARGET1_DYN_ADDR << 1)}` dynamic-address payload.
  - L100: frame descriptor `{LSM6DSV16X_STA, Direct_SETDASA, {data, 1}, LL_I3C_DIRECTION_WRITE}`.
  - L197/208: `HAL_I3C_AddDescToFrame` + `HAL_I3C_Ctrl_TransmitCCC_IT`.
- The same directory also contains 27 I3C examples, including ENTDAA dynamic enumeration, DMA-based SETDASA and IBI.

### [High confidence] The stm32duino/ISM6HG256X library has a clean transport abstraction

Repository structure:

```
ISM6HG256X/
├── library.properties           Depends on Wire + SPI (I3C not listed)
├── keywords.txt                 3.8 KB
├── examples/                    I2C/SPI examples
└── src/
    ├── ISM6HG256XSensor.h       322 lines   <-- transport layer
    ├── ISM6HG256XSensor.cpp     2852 lines  <-- sensor API
    ├── ism6hg256x_reg.c         ~326 KB  ST-generated register layer (do not modify)
    └── ism6hg256x_reg.h         ~209 KB  ST-generated register layer (do not modify)
```

- The ST standard driver (`ism6hg256x_reg.c/h`) uses function pointers (`stmdev_ctx_t { write_reg, read_reg, mdelay, handle }`) and is transport-agnostic.
- The C++ wrapper has only 2 files. Inside `IO_Read/IO_Write`, I²C / SPI use two branches selected by `dev_spi != NULL`.
- Adding a third I3C branch requires only a net addition of 50–60 lines.

## Complete HAL_I3C initialisation template (high confidence)

Extracted from the STM32CubeU3 NUCLEO-U385RG-Q I3C example; PB13/PB14 = I3C2, with internal pull-ups:

```c
I3C_HandleTypeDef hi3c2;

void I3C2_Init_Full(void) {
  /* 1. Enable the PWR clock (required before unlocking the latch) */
  __HAL_RCC_PWR_CLK_ENABLE();
  HAL_PWREx_EnablePullUpPullDownConfig();   // Unlock the PUCR latch
  HAL_PWREx_EnableI3CPullUp(PWR_I3CPU_PB13); // SCL
  HAL_PWREx_EnableI3CPullUp(PWR_I3CPU_PB14); // SDA

  /* 2. I3C2 clock source and clock gate */
  RCC_PeriphCLKInitTypeDef p = {0};
  p.PeriphClockSelection = RCC_PERIPHCLK_I3C2;
  p.I3c2ClockSelection   = RCC_I3C2CLKSOURCE_PCLK2;
  HAL_RCCEx_PeriphCLKConfig(&p);
  __HAL_RCC_I3C2_CLK_ENABLE();

  /* 3. GPIO mux: PB13/PB14 → AF6_I3C2, NOPULL (let PWR_I3CPU take control) */
  __HAL_RCC_GPIOB_CLK_ENABLE();
  GPIO_InitTypeDef g = {0};
  g.Pin = GPIO_PIN_13 | GPIO_PIN_14;
  g.Mode = GPIO_MODE_AF_PP;
  g.Pull = GPIO_NOPULL;
  g.Speed = GPIO_SPEED_FREQ_VERY_HIGH;
  g.Alternate = GPIO_AF6_I3C2;
  HAL_GPIO_Init(GPIOB, &g);
  HAL_Delay(1);  // Wait for the bus to become idle

  /* 4. Initialise the I3C controller core (parameters copied from the ST sensor example) */
  hi3c2.Instance = I3C2;
  hi3c2.Mode = HAL_I3C_MODE_CONTROLLER;
  hi3c2.Init.CtrlBusCharacteristic.SDAHoldTime        = HAL_I3C_SDA_HOLD_TIME_0_5;
  hi3c2.Init.CtrlBusCharacteristic.WaitTime           = HAL_I3C_OWN_ACTIVITY_STATE_0;
  hi3c2.Init.CtrlBusCharacteristic.SCLPPLowDuration   = 0x2F;
  hi3c2.Init.CtrlBusCharacteristic.SCLI3CHighDuration = 0x2F;
  hi3c2.Init.CtrlBusCharacteristic.SCLODLowDuration   = 0x2F;
  hi3c2.Init.CtrlBusCharacteristic.SCLI2CHighDuration = 0x00;
  hi3c2.Init.CtrlBusCharacteristic.BusFreeDuration    = 0x13;
  hi3c2.Init.CtrlBusCharacteristic.BusIdleDuration    = 0x5E;
  HAL_I3C_Init(&hi3c2);

  I3C_FifoConfTypeDef fifo = {HAL_I3C_RXFIFO_THRESHOLD_4_4, HAL_I3C_TXFIFO_THRESHOLD_1_4,
                              HAL_I3C_CONTROLFIFO_DISABLE, HAL_I3C_STATUSFIFO_DISABLE};
  HAL_I3C_SetConfigFifo(&hi3c2, &fifo);
  I3C_CtrlConfTypeDef ctrl = {0, 0, DISABLE, DISABLE, DISABLE, DISABLE, DISABLE, DISABLE};
  HAL_I3C_Ctrl_Config(&hi3c2, &ctrl);

  /* 5. Single-device SETDASA example (IMU0 static 0x6B → dynamic 0x32) */
  static uint8_t  setdasa_data[1] = { (0x32 << 1) };
  static uint32_t ctrlBuf[16];
  static uint8_t  txBuf[16];
  I3C_CCCTypeDef directCCC[] = {
    { 0x6B /*static addr*/, Direct_SETDASA,
      { setdasa_data, 1 }, LL_I3C_DIRECTION_WRITE }
  };
  I3C_XferTypeDef xfer = { {ctrlBuf, 16}, {txBuf, 1}, {NULL, 0} };
  HAL_I3C_AddDescToFrame(&hi3c2, directCCC, NULL, &xfer, 1,
                         I3C_DIRECT_WITHOUT_DEFBYTE_STOP);
  HAL_I3C_Ctrl_TransmitCCC_IT(&hi3c2, &xfer);
  while (HAL_I3C_GetState(&hi3c2) != HAL_I3C_STATE_READY) { }
  HAL_I3C_Ctrl_IsDeviceI3C_Ready(&hi3c2, 0x32, 300, 1000);
}
```

### SETDASA loop for 5 IMUs (pseudocode)

```c
const uint8_t DYN_ADDR[5] = {0x32, 0x33, 0x34, 0x35, 0x36};
const uint8_t TA0_GPIO[5] = {/* GPIO pin for each IMU's TA0 line */};

for (int i = 0; i < 5; i++) {
  // 1. Drive only IMU i's TA0 high (all others low) → that IMU's static address becomes 0x6B
  for (int j = 0; j < 5; j++)
    HAL_GPIO_WritePin(TA0_PORT, TA0_GPIO[j],
                      (i == j) ? GPIO_PIN_SET : GPIO_PIN_RESET);
  HAL_Delay(1);
  // 2. Send SETDASA to static address 0x6B, assigning dynamic address DYN_ADDR[i]
  setdasa_data[0] = DYN_ADDR[i] << 1;
  HAL_I3C_AddDescToFrame(...); HAL_I3C_Ctrl_TransmitCCC_IT(...);
  while (HAL_I3C_GetState(&hi3c2) != HAL_I3C_STATE_READY);
  HAL_I3C_Ctrl_IsDeviceI3C_Ready(&hi3c2, DYN_ADDR[i], 300, 1000);
}
// After completion, all 5 IMUs have distinct dynamic addresses
```

Note: ST's `HAL_I3C_Ctrl_DynAddrAssign` is for ENTDAA broadcast (not applicable when an IMU lacks a 48-bit PID). The standard approach for multiple ISM6HG256X devices sharing a bus is **not ENTDAA**, but Direct_SETDASA + TA0 GPIO selection as shown above.

### The 3 core APIs in one sentence each

- `HAL_I3C_Init(&hi3c)` — writes CFGR/TIMINGR and sets OD/PP clock dividers; it emits no bus signals.
- `HAL_I3C_AddDescToFrame(..., Direct_SETDASA, ...)` + `HAL_I3C_Ctrl_TransmitCCC_IT()` — assembles and sends the SETDASA CCC frame, once per IMU.
- `HAL_I3C_Ctrl_Transmit_IT` / `_Receive_IT` / `_MultipleTransfer_IT` — normal private-data reads/writes after dynamic addresses have been assigned.

### Path C: call HAL_I3C directly through `extern "C"` inside the sketch, **bypassing all library modifications** (tested on 5-22)

| Task | Time |
|---|---|
| Include HAL headers in the sketch + IRQ handlers + `HAL_I3C_MspInit` | 1–2 h |
| HAL_I3C init + GPIO AF6 mux + internal pull-up | 1–2 h |

| **Total (observed)** | **Completed within 5-22, approximately 6–9 h** |

The stm32duino/ISM6HG256X library **was not modified at all**. HAL_I3C was accessed directly through `extern "C" { #include "stm32u3xx_hal_i3c.h" }` inside the sketch. Path C was the shortcut omitted from the Path A estimate; once it worked, all library-modification effort was avoided. Full code: `firmware/imu_i3c_connectivity_5/imu_i3c_connectivity_5.ino`.

### Path B: use stm32duino's new 5-19 I3CBus library (merged into main, absent from release 2.12.0)

Reduced effort:

- No need to modify stm32duino/ISM6HG256X (use I3CBus to read ISM6HG256X registers directly).
- No need to implement HAL_I3C initialisation (`I3CBus.begin()` wraps it).
- A multi-device SETDASA wrapper and integration testing are still required.

Estimated **18–30 h**. **Risk:** the I3CBus library is only 3 days old, may have bugs, and has little documentation; time spent debugging the library itself may offset the savings.

## Key stm32duino + I3C sketch pitfalls

1. **Call `__HAL_RCC_PWR_CLK_ENABLE()` again yourself after `HAL_Init()` to unlock the PUCR latch**; otherwise `HAL_PWREx_EnableI3CPullUp` fails silently.
2. **Do not also call `Wire.begin()` on the same GPIO pair** — Wire takes over the alternate function for I2C, overwriting I3C AF6.
3. stm32duino's default `SystemClock_Config()` does not automatically enable the I3C clock gate, switch PB13/14 to AF6, or touch PWR_I3CPUCRx. All of these must be set explicitly in the sketch's setup().

## ST-LINK firmware upgrade on Windows (compared with the 5-17 Mac blocker)

- The Windows version of STM32CubeProgrammer **does not depend on libusb-1.0** (that is the Linux USB driver).
- ST-LINK V3 requires no additional driver from Win10 onwards.
- The Mac libusb pipe-stalled issue is unrelated to Windows and **will not recur** there.
- Anecdotal `LIBUSB_ERROR_PIPE` cases still exist. The standard fix is: “Install STSW-LINK009 + run a firmware upgrade once through STM32CubeProgrammer.”

**Pre-run Windows checklist:**

1. Install the STSW-LINK009 driver.
2. Run ST-LINK firmware upgrade once in the STM32CubeProgrammer GUI (if the Nucleo's factory firmware is old).
